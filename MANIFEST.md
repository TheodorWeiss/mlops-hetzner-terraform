# Манифест ML-системы — Citi Bike Availability Forecasting

**Проект:** автономный ML-сервис прогноза изменения доступности велосипедов на станциях байкшеринга на горизонте 1 час (на данных NYC Citi Bike); поверх прогноза вычисляется производный риск низкого наличия.
**Заявленный уровень зрелости ML-системы:** **2**.
**Команда:** 1 разработчик.
**Инфраструктура:** Hetzner Cloud (новый сервер, провижен через Terraform) + существующий сервер для сбора raw-данных.
**Репозиторий инфраструктуры:** github.com/TheodorWeiss/mlops-hetzner-terraform
**Дата:** июнь 2026.

---

## 1. Предыстория

Заказчик — оператор системы байкшеринга на примере NYC Citi Bike: крупной городской сети с тысячами станций и большим числом поездок в месяц. Основная операционная проблема оператора — **пространственно-временной дисбаланс парка**: велосипеды накапливаются в одних районах и заканчиваются в других.

Дисбаланс проявляется в двух формах:
- **Пустая станция** — пользователь не может взять велосипед, что приводит к упущенной поездке и снижению удовлетворённости.
- **Полная станция** — пользователь не может вернуть велосипед и вынужден искать соседнюю станцию со свободным доком.

Оператор решает эту проблему ребалансировкой — перемещением велосипедов между станциями. Но без краткосрочного прогноза ребалансировка остаётся **реактивной**: ресурсы направляются уже после того, как станция опустела или переполнилась. Задача проекта — перейти от реактивного управления парком к **упреждающему**: заранее выявлять станции с высоким риском дефицита велосипедов или свободных доков.

**Основной заказчик — оператор байкшеринга.** Пользовательская ценность возникает как вторичный эффект более надёжной работы системы.

## 2. Ценностное предложение

Продукт — ML-сервис, который для каждой станции прогнозирует **изменение количества доступных велосипедов на горизонте 1 час** и на его основе — ожидаемое наличие велосипедов через час. Поверх прогноза вычисляется производный сигнал **риска низкого наличия** (велосипедов почти не останется).

Ценность для оператора:
- более раннее выявление станций, требующих ребалансировки;
- потенциальное снижение числа упущенных поездок из-за пустых станций;
- более рациональное планирование рейсов ребалансировки.

Ценность для пользователя:
- более надёжная информация о наличии велосипеда к моменту прибытия;
- снижение риска ситуации, когда пользователь приходит к станции, но не может начать поездку.

Горизонт **1 час** выбран как операционный горизонт MVP: он совпадает с естественной часовой агрегацией данных о поездках, достаточно короткий, чтобы прогноз оставался актуальным, и достаточно длинный, чтобы оператор успел среагировать. Риск переполнения (нет свободных доков) — возможное расширение, в MVP не основной выход.

## 3. Цели и ключевые задачи

1. **Прогноз изменения наличия.** Обучить модель, предсказывающую **нетто-изменение** числа доступных велосипедов на станции за час: `delta_bikes_1h = returns_1h − departures_1h`. Источник чистой исторической разметки — trip CSV Citi Bike, где каждая строка — отдельная поездка с явными `start_station_id`, `end_station_id`, `started_at`, `ended_at` (departures/returns агрегируются по станция-час).

2. **Прогноз наличия от реальной точки.** Соединить прогноз изменения с **фактическим** текущим наличием из live GBFS:
   ```
   predicted_bikes_1h = current_bikes_now + predicted_delta_bikes_1h
   predicted_bikes_1h = clip(predicted_bikes_1h, 0, capacity)
   ```
   `current_bikes_now` — факт из снепшота (не прогноз), модель добавляет только изменение. Поверх вычисляется производный `low_availability_risk = predicted_bikes_1h ≤ порог`.

3. **Интеграция исторических и live-данных.** Связать два источника с разными ключами: historical CSV использует legacy-id, live GBFS — UUID-like `station_id`. Компонент `station_id_mapping` на основе `station_information.short_name` (в актуальном GBFS: coverage `short_name` = 1.0000, дублей 0). Для строк historical trip CSV coverage контролируется отдельно после фильтрации служебных/внешних станций (`SYS*`, `JC*`, `Shop Morgan`).

4. **Самообновляемость модели.** Автоматизированный цикл: загрузка нового месячного CSV → построение признаков → обучение candidate-модели → **переоценка текущего champion на том же новом тест-месяце** → promotion только если candidate не хуже champion по primary-метрике с порогом. При деградации — rollback переключением MLflow-alias на предыдущую стабильную версию.

5. **Сервинг и мониторинг.** Отдавать прогноз через API; вести два контура метрик — офлайн (на чистой разметке раз в месяц) и онлайн (прогноз наличия против фактических снепшотов).

## 4. Решение

**Что это.** MVP автономного ML-сервиса, демонстрирующий **полный production-lifecycle модели**: от приёма данных и обучения до сервинга, мониторинга и контролируемой замены деградировавшей модели. Не «production-система как в реальной компании», а учебный, но архитектурно полноценный сервис, проходящий весь цикл MLOps.

**Заявленный уровень зрелости — 2.** Каждый признак уровня 2 закрыт конкретным компонентом:

| Признак уровня 2 | Реализация |
|---|---|
| Версионирование кода | Git / GitHub |
| CI/CD выкатки на прод | GitHub Actions (lint/тесты/сборка/деплой) |
| Фича-стор | feature-таблицы в Postgres (привязаны к временным окнам и source month); Feast-versioning — stretch |
| Сервинг через API | FastAPI (`/health`, `/predict/station`, `/predict/batch`) |
| Мониторинг качества | `model_evaluation_runs` + `prediction_log` + health-checks/логи; Prometheus/Grafana и Evidently — stretch |
| Управление экспериментами | MLflow (tracking + model registry, alias champion/challenger) |
| Оркестратор | Airflow (DAG приёма, обучения, оценки, промоута) |

**Состав компонентов:**

*Must-have для финальной защиты:*
- Оркестратор: **Airflow** (ingestion-bridge DAG, monthly retraining DAG)
- Эксперименты/реестр: **MLflow** (tracking + model registry, alias champion/challenger)
- Feature store: **feature-таблицы в Postgres**, привязанные к временным окнам и source month; полноценный feature-store/versioning через Feast — stretch
- Storage: **Postgres** (mapping, feature tables, prediction logs, eval runs) + **MinIO** (raw, parquet, models, reports)
- Сервинг: **FastAPI** (`/health`, `/predict/station`, `/predict/batch`)
- Мониторинг (lightweight): **`model_evaluation_runs` + `prediction_log`** + health-checks/логи + `check_upstream_freshness`
- CI/CD: **GitHub Actions**
- IaC: **Terraform** (провижен сервера/firewall/volume) + **docker-compose** (стек)
- Базовый Data Quality: проверки в парсерах (флаги, `last_reported`, аномалии поездок) с записью DQ-счётчиков в лог-таблицы

Статус: **реализовано** — Airflow, MLflow, Postgres, MinIO, Terraform/docker-compose, monthly retraining DAG, structured-слой, ingestion-bridge, feature engineering, production-compatible модель (LightGBM delta + weather) и XGBoost-челленджер. **В работе** — честный quality gate с переоценкой текущего champion на новом тест-месяце, FastAPI, GitHub Actions, SLI/SLO, ADR.

*Stretch (строим по остатку времени; не заявляются как готовые, пока не работают):*
- **Feast** как полноценный feature-store-адаптер поверх Postgres feature tables
- **Great Expectations** — формализация DQ-проверок в suite
- **Evidently** — drift/quality HTML-отчёты в MinIO
- **Prometheus + Grafana** — технические дашборды
- **Nginx** reverse proxy
- **Superset** (BI-кабинет оператора), **OpenMetadata/DataHub** (data catalog) — явно вне scope MVP

Принцип: всё, что в must-have, к защите реально работает (`docker ps` healthy, `/health`=200). Stretch-компоненты присутствуют на схеме архитектуры как план развития и повышаются до must-have только по факту реализации.

**IaC — двухслойный.** **Terraform** провиженит облачные ресурсы Hetzner (сервер, firewall, volume, SSH-ключ) — он создаёт инфраструктуру и обеспечивает воспроизводимость и teardown через `terraform destroy`. **docker-compose** разворачивает стек сервисов на провижененном сервере. Слои не дублируются: Terraform отвечает за существование ресурсов, compose — за работающие контейнеры.

**Ключевые фичи продукта:**
- Прогноз `delta_bikes_1h` → `predicted_bikes_1h = current_bikes + delta`, clip в `[0, capacity]` → производный `low_availability_risk`.
- `station_id_mapping` (legacy `short_name` → GBFS `station_id` + метаданные) как часть data-слоя.
- Champion/challenger с честным quality gate (переоценка champion на том же тест-месяце); rollback переключением alias.
- Месячное переобучение на свежем CSV; live GBFS — текущая точка отсчёта и мониторинг свежести.

**Интеграции:** live GBFS (`station_status`, `station_information`), historical trip CSV (S3), погодный API (Open-Meteo: архив для train, forecast для inference). Календарь праздников и `region_id` — future-фичи (в MVP-модель не входят).

**Ограничения (осознанные упрощения MVP):**
- Облако — экономичное (сервис должен жить до защиты).
- Прогноз только на горизонт 1 час (совпадает с часовой агрегацией данных).
- Ребалансировка не моделируется: нет данных о действиях оператора и правилах перемещения. В MVP такие события рассматриваются как внешняя ненаблюдаемая причина ошибки прогноза; их влияние отслеживается через online-метрики (bias/MAE наличия).
- «Live»-демонстрация автоцикла переобучения опирается на реальное ежемесячное появление нового CSV (подтверждено на практике).

**Что НЕ входит в продукт:**
- Графовые нейросети / SOTA spatiotemporal модели.
- Прогноз на горизонты >60 минут и мульти-день.
- Моделирование ребалансировки и маршрутизации грузовиков.
- Отдельный прогноз риска переполнения доков (возможное расширение).
- Монетизация, биллинг, мобильное приложение, продакшн-фронтенд.
- Отдельные модели по типам велосипедов.
- SLA коммерческого уровня, мульти-регион, production-отказоустойчивость.

## 5. Осуществимость

**Команда и сроки.** Один разработчик. Декомпозиция по этапам: данные → baseline → компоненты MLOps → IaC → автоцикл+переключение → CI/CD → мониторинг+SLI/SLO → облако → MDD/ADR → документация → защита.

**Что уже сделано (снижает риск):**
- Источники данных проверены: live GBFS работает, historical CSV скачивается, mapping через `short_name` подтверждён (coverage >98%, `short_name` уникален).
- Зафиксирован класс моделей (градиентный бустинг, LightGBM основной) и набор фичей — по открытым исследованиям, без R&D.
- Коллектор снепшотов работает (сбор ~каждые 2–5 мин).
- **Инфраструктура провижена через Terraform:** новый сервер Hetzner CX33 (4 vCPU, 8 GB RAM, 80 GB SSD, Ubuntu 24.04, nbg1), отдельный volume 50 GB на `/mnt/mlops-data`, swap 4 GB, Docker + Compose, минимальный firewall (22 с одного IP, 80/443), доступ по SSH под `deploy`. Старый сервер в Terraform не описан и не затронут.

**Ресурсы:**
- Облачный хостинг: Hetzner CX33 (почасовой биллинг; после защиты `terraform destroy`).
- Compute: датасет небольшой (месяц поездок ≈ ~1 млн строк, агрегаты по станцие-часам — десятки-сотни тыс. строк), LightGBM обучается за секунды-минуты, GPU не нужен.
- Бесплатные API: GBFS (без ключа), погода (free tier), CSV с S3 (открыто).

**Основные риски и митигация:**
- *Падение точности при замене trip-лагов на online-доступные фичи* → честно фиксируем: offline lag-модель остаётся benchmark (потолок качества), production-модель использует только онлайн-доступные фичи (время/гео/погода) + факт current_bikes.
- *Сервис «упал» к защите* → дешёвый хостинг + `/health` + IaC для быстрого пере-развёртывания.
- *Качество/свежесть live-данных* → DQ-проверки в парсерах + `check_upstream_freshness` (чтение `collector_status.json` + возраст снепшота) + флаг `stale_state` в ответах API.
- *Несовпадение станций CSV↔GBFS* → снят через `station_id_mapping` (coverage 1.0000).

**Текущий статус реализации (на момент манифеста):** провижена инфраструктура (Terraform), поднят стек (Postgres/MinIO/MLflow/Airflow), работает ingestion-bridge, structured-слой GBFS, historical trip ingestion (фев–апр + автоподхват нового месяца), feature engineering, обучены модели, champion/challenger в MLflow, monthly retraining DAG. В работе: production-compatible модель, FastAPI, SLI/SLO, ADR.

## 6. Данные

**Источник обучающих данных (offline, train):**
- **Historical trip CSV** (`s3.amazonaws.com/tripdata/`, помесячно, возможны part-файлы) — основной источник чистой разметки.
- **`station_information.json`** (GBFS) — метаданные станций: `short_name` (мост к legacy-id), `capacity`, `lat/lon`, `region_id`.
- **Обогащение:** погодный API (Open-Meteo: температура, осадки — архив для train, forecast для inference). Праздники — future-фича.

**Источник реальных данных (online, prod):**
- **Live GBFS `station_status`** — снепшоты каждые ~2–5 мин (собственный коллектор на старом сервере): `num_bikes_available`, `num_ebikes_available`, `num_docks_available`, `*_disabled`, флаги `is_*`, `last_reported`.

**Процесс разметки (автоматический, без ручного труда):**
- **Target модели (регрессия):** из trip CSV агрегируются `departures`/`returns` по станция-час, target = `delta_bikes_1h = returns_1h − departures_1h`. Чистый ground truth, доступен раз в месяц с новым CSV.
- **Online ground truth (для продуктовых метрик):** фактическое `num_bikes_available` через час из будущего снепшота. Доступно непрерывно — позволяет сравнивать `predicted_bikes_1h` с фактом без ожидания месячного CSV.

**Связывание источников.** `station_id_mapping`: `trip.start/end_station_id` → `station_information.short_name` → GBFS `station_id` + метаданные. Маппинг однозначен (дублей `short_name` нет).

**Качество данных.** В MVP реализовано как проверки в парсерах с записью DQ-счётчиков в лог-таблицы (`gbfs_ingestion_log`, `trip_ingestion_log`): активные станции (флаги=1), `last_reported ≠ 86400` и freshness (`data_age` порог), неотрицательные счётчики, уникальность `station_id` в снепшоте, e-bikes ⊆ bikes, фильтр аномальных поездок (нулевая/отрицательная/`>24ч` длительность, пропуски станций), контроль coverage маппинга. Формализация этих правил в **Great Expectations** suite — stretch.

**Два контура.** Обучение/переобучение — на месячном CSV (чистый target `delta_bikes`); online-контур (снепшоты) — текущая точка отсчёта `current_bikes` для прогноза + фактическое наличие для продуктовых метрик + мониторинг свежести.

**Статус валидации данных.** Данные прошли валидацию на боевых данных: `station_id_mapping` через `short_name` — в актуальном GBFS coverage `short_name` = 1.0000, дублей 0 (coverage строк trip CSV контролируется отдельно после фильтрации служебных станций); загружены фев–апр 2026 (~2.5 млн станция-час строк), автоподхват нового месяца подтверждён. Главный риск интеграции источников снят.

## 7. Метрики

**Главная бизнес-метрика: service failure rate** — доля (станция × снепшот ~5 мин)-слотов, когда станция практически недоступна для взятия велосипеда: `num_bikes_available ≤ 1`. Порог `≤1` — operational threshold «практической недоступности» (`num_bikes_available` — уже функциональные велосипеды). Чувствительность проверяется на `{0, ≤1, ≤2}`.

В MVP это **мониторимая (proxy) бизнес-метрика**, а не напрямую оптимизируемый моделью таргет: модель предсказывает изменение наличия, а service failure rate измеряет, насколько часто станции реально доходят до дефицита. Связь — через производный сигнал `low_availability_risk` на основе `predicted_bikes_1h`.

Система — **предиктор, а не актуатор**: сам прогноз не снижает service failure rate напрямую, бизнес-эффект возникает при использовании сигнала оператором для ребалансировки. Операционно-атрибутируемые метрики (на онлайн-данных):

1. **Advance detection rate** — доля фактических событий низкого наличия, для которых модель заранее (за час) выдала сигнал высокого риска.
2. **False-alarm rate** — доля ложных тревог среди сигналов высокого риска (важно: лишние тревоги = неэффективные рейсы ребалансировки).
3. **Potentially prevented lost trips** — proxy-оценка спасённых поездок при действии по сигналу (backtest-оценка, не causal без A/B).

**Связка «бизнес → ML»:**
```
качество модели (офлайн)         качество прогноза наличия (онлайн)      бизнес-эффект
MAE/RMSE/bias на          →      MAE/bias predicted_bikes,        →     ↑ advance detection,
delta_bikes_1h                   precision/recall/F1 по порогу          ↓ false alarms,
                                 низкого наличия                        ↓ service failure rate
```
Офлайн-качество модели изменения влияет на качество прогноза наличия в проде, а оно — на операционные бизнес-метрики.

## 8. Оценка качества модели

Два контура, соответствующие двум источникам ground truth.

**Офлайн-метрики (на чистой разметке, при месячном переобучении).**
Target — `delta_bikes_1h`.
- **Primary: MAE_delta** (интерпретируемо: «прогноз изменения в среднем ошибается на N велосипедов»).
- **Secondary: RMSE_delta** (контроль крупных промахов).
- **Diagnostic: bias_delta** (систематическое смещение — важно: стабильный положительный bias = оптимистичный прогноз наличия).
- **Baseline:** zero-change (`delta = 0`) и «вчера в этот час». Модель обязана бить baseline; сравнение фиксируется в ADR.
- Срезы: по часам, дням недели, типам станций.

**Онлайн-метрики (продуктовые, непрерывно).**
Сравнение `predicted_bikes_1h` с фактическим наличием через час из снепшота:
- **MAE / RMSE наличия** (основная online-метрика: «прогноз наличия ошибается на N велосипедов»).
- **bias наличия** (систематическая пере/недооценка).
- **Производные precision / recall / F1** по событию низкого наличия: `predicted_low = predicted_bikes ≤ порог` против `actual_low = actual_bikes ≤ порог`. F1 здесь законен, т.к. метки `actual_low` приходят из фактических снепшотов непрерывно.
- Реализация: каждый прогноз пишется в `prediction_log` (`predicted_at`, `target_time`, `current_bikes_at_predict`, `predicted_delta`, `predicted_bikes`); постфактум джойн с фактом → ошибка; агрегация на скользящем окне.
- **Деградация → триггер:** падение online-MAE наличия (или F1 по порогу) ниже SLO на скользящем окне → алерт/сигнал к переобучению.

**Валидация:** только **time-series split**; **rolling backtest** (train месяцы → test следующий месяц) — даёт кривую обучения и материал для champion/challenger.

**Гейт промоута (честный).** При появлении нового месяца: (1) текущий champion **переоценивается на том же новом тест-месяце**; (2) обучается candidate (LightGBM) и challenger (XGBoost), оцениваются на том же месяце; (3) candidate → champion **только если** `candidate_MAE ≤ champion_MAE(на том же месяце) × 0.99` И `candidate_MAE < baseline_MAE`; иначе champion сохраняется. Rollback — переключение MLflow-alias `@champion` на предыдущую версию.

## 9. Подбор модели (итеративно)

- **Итерация 0 — Baseline.** Zero-change (`delta = 0`) и «вчера в этот час». Нижняя граница, которую всё обязано бить.
- **Итерация 1 — Offline benchmark (LightGBM на trip-лагах).** Target = departures/returns, фичи включают `lag_1h/24h/168h`. Показала, что в данных есть сильный сигнал (MAE потоков ~1.73 против baseline ~3.33). **Не идёт в serving** — её trip-лаги недоступны в реальном времени. Роль: верхняя граница качества (upper bound) для MDD/ADR.
- **Итерация 2 — Production-модель (LightGBM, основная).** Target = `delta_bikes_1h`. **Фичи MVP** (только онлайн-доступные): `hour`, `day_of_week`, `is_weekend`, `month` (локальное NY-время), `lat`, `lon`, `capacity`, погода. Соблюдён **feature contract: train features = inference features**. Погода: исторический архив для train, **forecast на целевой час для inference** — это осознанно принятый для MVP train/serving skew, зафиксирован как ограничение. **Stretch/future фичи:** `region_id`, праздники, соседние станции, доля e-bike. Это champion для serving.
- **Итерация 3 — Тюнинг** через time-series CV.
- **Итерация 4 — XGBoost-челленджер** для production-модели — проверка устойчивости выбора LightGBM в рамках champion/challenger.

**Вне scope:** LSTM/CNN-LSTM и графовые сети; прямая модель риска на накопленных снепшотах — возможное развитие, когда накопится онлайн-история.

**Артефакты:** все итерации логируются в MLflow. Offline benchmark помечается как `benchmark` (не serving); production-модель — под alias `@champion`.

## 10. Инференс

Система сочетает оба режима, потому что продуктовая логика требует online-прогноза, а обучение и мониторинг естественно выполняются batch-пайплайнами.

**Real-time (online) — основной для продукта.**
- FastAPI: `POST /predict/station` (вход: `station_id`, горизонт 1ч), `POST /predict/batch`. Логика: взять `current_bikes` из последнего GBFS-снепшота (факт) + фичи (время/гео/погода-forecast) → champion-модель даёт `predicted_delta_bikes_1h` → `predicted_bikes_1h = clip(current_bikes + delta, 0, capacity)` → производный `low_availability_risk`.
- Ответ включает `predicted_delta_bikes_1h`, `predicted_bikes_1h`, `low_availability_risk`, **`stale_state`** (если снепшот устарел) и `state_age_seconds`.
- Champion-модель загружается из MLflow при старте сервиса и используется из памяти.
- `GET /health` для проверки живости. Допустимая задержка — единицы секунд.

**Batch (offline).**
- Airflow по расписанию: приём снепшотов и нового CSV, сборка фичей, переобучение, оценка, периодический пакетный пересчёт прогнозов по станциям в `prediction_log`.
- Месячное переобучение на свежем CSV — batch.

**Распределение по серверам.** Сбор raw-снепшотов остаётся на существующем сервере (данные переживают `terraform destroy`). Новый Terraform-managed сервер несёт MLOps-стек и обработку. Рекомендуемая логика: старый сервер собирает raw каждые ~5 мин, новый забирает/обрабатывает каждые ~15 мин.

## 11. Обратная связь

**Источники обратной связи для следующей итерации:**
1. **Фактическое наличие из снепшотов** (через час) — непрерывная online-оценка прогноза наличия (MAE/bias + F1 по порогу). Не подменяет чистый target `delta_bikes` из CSV, а оценивает продуктовый выход.
2. **Месячный trip CSV** — чистый ground truth; запускает переобучение и честную переоценку champion.
3. **`check_upstream_freshness`** — здоровье upstream (`collector_status.json` + возраст снепшота) → флаг stale/алерт.
4. **DQ-счётчики** в лог-таблицах — рост доли отфильтрованных/stale-станций. (Дрейф через Evidently — stretch.)

Цикл: появление нового месяца → retraining DAG → переоценка champion на новом месяце → candidate vs champion на одном окне → promotion (alias `@champion`) или сохранение текущего → при необходимости rollback переключением alias.

**MDD — Да.** Архитектурные решения — на основе метрик: выбор модели через сравнение с baseline и benchmark; промоут через честный quality gate; ключевые решения оформляются как **ADR**. Запланированные ADR: (1) latency — расчёт признаков on-demand vs готовые из feature store (два набора latency, H0/H1, статтест, p-value, решение); (2) выбор serving-архитектуры — offline benchmark (trip-лаги) vs production-модель (онлайн-доступные фичи), обоснование через feature contract.
