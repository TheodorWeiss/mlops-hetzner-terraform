# Манифест ML-системы — Citi Bike Availability Risk Forecasting

**Проект:** автономный ML-сервис прогноза риска дефицита велосипедов и свободных доков в системе байкшеринга (на данных NYC Citi Bike).
**Заявленный уровень зрелости ML-системы:** **2**.
**Команда:** 1 разработчик.
**Инфраструктура:** Hetzner Cloud (новый сервер, провижен через Terraform) + существующий сервер для сбора raw-данных.
**Репозиторий инфраструктуры:** github.com/TheodorWeiss/mlops-hetzner-terraform
**Дата:** июнь 2026.

---

## 1. Предыстория

Заказчик — оператор системы байкшеринга на примере NYC Citi Bike: крупной городской сети с тысячами станций и большим числом поездок в месяц. Основная операционная проблема оператора — **пространственно-временной дисбаланс парка**: велосипеды накапливаются в одних районах и заканчиваются в других.

Дисбаланс проявляется в двух формах:
- **Пустая станция** — пользователь не может взять велосипед, что приводит к упущенной поездке и снижению удовлетворённости.
- **Полная станция** — пользователь не может вернуть велосипед и вынужден искать соседнюю станцию со свободным доком.

Оператор решает эту проблему ребалансировкой — перемещением велосипедов между станциями. Но без краткосрочного прогноза ребалансировка остаётся **реактивной**: ресурсы направляются уже после того, как станция опустела или переполнилась. Задача проекта — перейти от реактивного управления парком к **упреждающему**: заранее выявлять станции с высоким риском дефицита велосипедов или свободных доков.

**Основной заказчик — оператор байкшеринга.** Пользовательская ценность возникает как вторичный эффект более надёжной работы системы.

## 2. Ценностное предложение

Продукт — ML-сервис, который для каждой станции прогнозирует риск дефицита велосипедов и риск отсутствия свободных доков на горизонтах **15 и 60 минут**.

Ценность для оператора:
- более раннее выявление станций, требующих ребалансировки;
- потенциальное снижение числа упущенных поездок из-за пустых станций;
- потенциальное снижение числа проблемных возвратов из-за переполненных станций;
- более рациональное планирование рейсов ребалансировки.

Ценность для пользователя:
- более надёжная информация о наличии велосипеда/свободного дока к моменту прибытия;
- снижение риска ситуации, когда пользователь приходит к станции, но не может начать или завершить поездку.

Горизонты выбраны по двум практическим сценариям. **15 минут** — пользовательский сценарий «дойти до станции / скоро прибыть». **60 минут** — операционный горизонт MVP для планирования ребалансировки: достаточно короткий, чтобы прогноз оставался актуальным, и достаточно длинный, чтобы оператор успел среагировать.

## 3. Цели и ключевые задачи

1. **Прогноз потоков поездок.** Обучить модели спроса и возвратов по станциям: `departures_next_15/60min` и `returns_next_15/60min`. Источник чистой исторической разметки — trip CSV Citi Bike, где каждая строка — отдельная поездка с явными `start_station_id`, `end_station_id`, `started_at`, `ended_at`.

2. **Оценка риска дефицита.** Объединить прогноз потоков с текущей доступностью из live GBFS по балансовой логике:
   ```
   predicted_bikes_60min = current_bikes − pred_departures_60min + pred_returns_60min
   risk_empty_60min      = predicted_bikes_60min ≤ threshold

   predicted_docks_60min = current_docks + pred_departures_60min − pred_returns_60min
   risk_full_60min       = predicted_docks_60min ≤ threshold
   ```
   На выходе — продуктовые показатели `risk_empty` и `risk_full` на 15 и 60 минут.

3. **Интеграция исторических и live-данных.** Связать два источника с разными ключами: historical CSV использует legacy-id, live GBFS — UUID-like `station_id`. Вводится компонент `station_id_mapping` на основе `station_information.short_name` (проверено: уникален, coverage ≈98.85% по станциям и >98% по строкам поездок). Фильтрация служебных (`SYS*`, `JC*`, `Shop Morgan`) и stale-станций.

4. **Самообновляемость модели.** Автоматизированный цикл: загрузка новых данных → построение признаков → обучение candidate-модели → сравнение с текущей champion → promotion только при прохождении quality gate на hold-out/backtest. При деградации текущей модели — rollback или переключение на последнюю стабильную версию.

5. **Сервинг и мониторинг.** Отдавать прогноз риска через API; отслеживать технические и бизнес-метрики. Live GBFS snapshots — для online-фичей и мониторинга availability-рисков; чистые labels для demand/returns — из historical trip CSV.

## 4. Решение

**Что это.** MVP автономного ML-сервиса, демонстрирующий **полный production-lifecycle модели**: от приёма данных и обучения до сервинга, мониторинга и контролируемой замены деградировавшей модели. Не «production-система как в реальной компании», а учебный, но архитектурно полноценный сервис, проходящий весь цикл MLOps.

**Заявленный уровень зрелости — 2.** Каждый признак уровня 2 закрыт конкретным компонентом:

| Признак уровня 2 | Реализация |
|---|---|
| Версионирование кода | Git / GitHub |
| CI/CD выкатки на прод | GitHub Actions (сборка, тесты, деплой) |
| Фича-стор | Feast + feature-таблицы в Postgres |
| Сервинг через API | FastAPI (`/predict/station`, `/predict/batch`, `/health`) |
| Мониторинг качества | Prometheus + Grafana (тех/опер), Evidently (drift/quality) |
| Управление экспериментами | MLflow (tracking + model registry) |
| Оркестратор | Airflow (DAG приёма, обучения, оценки, промоута) |

**Состав компонентов:**

*Must-have (строим, деплоим, защищаем):*
- Оркестратор: **Airflow**
- Эксперименты/реестр: **MLflow**
- Feature store: **Feast** (+ feature-таблицы в Postgres)
- Storage: **Postgres** (metadata, prediction logs, feature tables) + **MinIO** (raw, parquet, models, reports)
- Качество данных: **Great Expectations** (движок блока Data Quality Validation)
- Сервинг: **FastAPI** + **Nginx**
- Мониторинг: **Prometheus + Grafana**, **Evidently**
- CI/CD: **GitHub Actions**
- IaC: **Terraform** (провижен сервера/firewall/volume) + **docker-compose** (стек)

*Stretch (на схеме архитектуры, строим по остатку времени):*
- Superset (BI-кабинет оператора)
- OpenMetadata / DataHub (data catalog) — явно вне scope MVP

**IaC — двухслойный.** **Terraform** провиженит облачные ресурсы Hetzner (сервер, firewall, volume, SSH-ключ) — он создаёт инфраструктуру и обеспечивает воспроизводимость и teardown через `terraform destroy`. **docker-compose** разворачивает стек сервисов на провижененном сервере. Слои не дублируются: Terraform отвечает за существование ресурсов, compose — за работающие контейнеры.

**Ключевые фичи продукта:**
- Прогноз `departures/returns` (15/60 мин) → балансовый расчёт `risk_empty/risk_full`.
- `station_id_mapping` (legacy `short_name` → GBFS `station_id` + метаданные) как часть data-слоя.
- Champion/challenger с quality gate; при деградации — rollback / переключение трафика.
- Двухуровневое переобучение: чистое (месячный CSV) + online-мониторинг (live снепшоты).

**Интеграции:** live GBFS (`station_status`, `station_information`), historical trip CSV (S3), погодный API, календарь праздников.

**Ограничения (осознанные упрощения MVP):**
- Подмножество крупных станций или географические кластеры, не все ~2400 сразу.
- Облако — экономичное (сервис должен жить до защиты).
- «Live»-демонстрация автоцикла деградация→замена выполняется ускоренно через backtest на исторических месяцах.

**Что НЕ входит в продукт:**
- Графовые нейросети / SOTA spatiotemporal модели.
- Прогноз на горизонты >60 минут и мульти-день.
- Ребалансировка как отдельная сущность (только флаг по паттерну скачков).
- Маршрутизация грузовиков ребалансировки, оптимизация логистики.
- Монетизация, биллинг, мобильное приложение, продакшн-фронтенд.
- Отдельные модели по типам велосипедов; доля e-bike — только фича.
- SLA коммерческого уровня, мульти-регион, production-отказоустойчивость.

## 5. Осуществимость

**Команда и сроки.** Один разработчик. Декомпозиция по этапам: данные → baseline → компоненты MLOps → IaC → автоцикл+переключение → CI/CD → мониторинг+SLI/SLO → облако → MDD/ADR → документация → защита.

**Что уже сделано (снижает риск):**
- Источники данных проверены: live GBFS работает, historical CSV скачивается, mapping через `short_name` подтверждён (coverage >98%, `short_name` уникален).
- Зафиксирован класс моделей (градиентный бустинг, LightGBM основной) и набор фичей — по открытым исследованиям, без R&D.
- Коллектор снепшотов работает (сбор ~каждые 2–5 мин).
- **Инфраструктура провижена через Terraform:** новый сервер Hetzner CX33 (4 vCPU, 8 GB RAM, 80 GB SSD, Ubuntu 24.04, nbg1), отдельный volume 50 GB на `/mnt/mlops-data`, swap 4 GB, Docker + Compose, минимальный firewall (22 с одного IP, 80/443), доступ по SSH под `deploy`. Старый сервер в Terraform не описан и не затронут.

**Ресурсы:**
- Облачный хостинг: Hetzner CX33 (почасовой биллинг; после защиты `terraform destroy`).
- Compute: датасет небольшой (месяц поездок ≈ ~1 млн строк, агрегаты по станцие-часам — десятки-сотни тыс. строк), LightGBM обучается за секунды-минуты, GPU не нужен.
- Бесплатные API: GBFS (без ключа), погода (free tier), CSV с S3 (открыто).

**Основные риски и митигация:**
- *Разреженность таргета на 15 мин для мелких станций* → начать с крупных станций/кластеров; при необходимости агрегировать горизонт/таргет.
- *Сервис «упал» к защите* → дешёвый хостинг + `/health` + IaC для быстрого пере-развёртывания.
- *Качество live-данных* → блок Data Quality Validation (флаги, freshness, флаг ребалансировки).
- *Несовпадение станций CSV↔GBFS* → снят через `station_id_mapping`.

## 6. Данные

**Источник обучающих данных (offline, train):**
- **Historical trip CSV** (`s3.amazonaws.com/tripdata/`, помесячно, возможны part-файлы) — основной источник чистой разметки.
- **`station_information.json`** (GBFS) — метаданные станций: `short_name` (мост к legacy-id), `capacity`, `lat/lon`, `region_id`.
- **Обогащение:** погодный API (температура, осадки), календарь праздников.

**Источник реальных данных (online, prod):**
- **Live GBFS `station_status`** — снепшоты каждые ~2–5 мин (собственный коллектор на старом сервере): `num_bikes_available`, `num_ebikes_available`, `num_docks_available`, `*_disabled`, флаги `is_*`, `last_reported`.

**Процесс разметки (автоматический, без ручного труда):**
- **Таргеты спроса/возвратов (регрессия):** агрегация `started_at`→`departures` и `ended_at`→`returns` по (станция, временной бакет) из trip CSV. Чистый ground truth.
- **Метки availability-риска (продуктовый выход / online-мониторинг):** delayed labels из будущих снепшотов — фактические `num_bikes/docks_available` через 15/60 мин.

**Связывание источников.** `station_id_mapping`: `trip.start/end_station_id` → `station_information.short_name` → GBFS `station_id` + метаданные. Маппинг однозначен (дублей `short_name` нет).

**Качество данных (Great Expectations).** Правила как тестируемые expectations с отчётами: активные станции (флаги=1), `last_reported ≠ 86400` и freshness (`data_age` порог), неотрицательные счётчики, уникальность `station_id` в снепшоте, e-bikes ⊆ bikes, фильтр аномальных поездок (нулевая/отрицательная/`>24ч` длительность, пропуски станций), флаг `suspected_rebalancing` по скачкам, проверка `capacity_gap`, контроль coverage маппинга.

**Два контура обновления.** Чистое обучение/переобучение — на месячном CSV; online-контур (снепшоты) — фичи в реальном времени + мониторинг + delayed availability-labels.

**Статус валидации данных.** Данные прошли первичную валидацию и признаны пригодными для MVP. Снят главный риск интеграции источников (station_id mapping). До этапа обучения проверяются: распределение demand/returns, аномалии поездок, part-файлы за месяц, capacity_gap, baseline-физибилити.

## 7. Метрики

**Главная бизнес-метрика: service failure rate** — доля (станция × снепшот ~5 мин)-слотов, когда станция практически недоступна для одного из ключевых действий: взять или вернуть велосипед. Раскладывается на:
- **empty rate** — доля слотов с `num_bikes_available ≤ 1`;
- **full rate** — доля слотов с `num_docks_available ≤ 1`.

Порог `≤1` выбран как operational threshold «практической недоступности» (`num_bikes_available` — уже функциональные велосипеды, поэтому ≤1 = не более одного рабочего). Чувствительность проверяется на `{0, ≤1, ≤2}`.

Система — **предиктор, а не актуатор**: сам прогноз не снижает service failure rate напрямую, бизнес-эффект возникает только при использовании сигнала оператором для ребалансировки. Поэтому фиксируются операционно-атрибутируемые метрики:

1. **Advance detection rate** — доля фактических событий дефицита, для которых модель заранее выдала actionable alert на горизонте 15/60 мин.
2. **False-alarm rate** — доля ложных тревог среди сигналов высокого риска после выбора operational threshold (важно: лишние тревоги = неэффективные рейсы ребалансировки).
3. **Potentially prevented lost trips** — proxy-оценка спасённых поездок при действии по сигналу. Допущение: при empty-состоянии число упущенных аренд оценивается по типичному спросу станции в этот час из исторических данных. Это backtest-оценка, не causal без A/B.
4. **Service failure rate after policy simulation** — empty/full rate в backtest-сценарии «до/после» применения простой политики ребалансировки на сигналах модели.

**Связка «бизнес → ML»:**
```
качество прогноза потоков        качество риск-сигнала              бизнес-эффект
MAE/RMSE/RMSLE на             →  precision/recall/PR-AUC       →  ↑ advance detection,
departures/returns               на risk_empty / risk_full         ↓ false alarms,
                                                                   ↓ service failure rate
```
Офлайн-качество моделей спроса и возвратов влияет на качество риск-классификации, а оно — на операционные бизнес-метрики.

## 8. Оценка качества модели

**Офлайн-метрики (перед деплоем).**

*Слой 1 — регрессия потоков (`departures/returns`, 15/60 мин):*
- **Primary: MAE** (интерпретируемо: «ошибка в среднем на N поездок»).
- **Secondary: RMSLE** (при скошенном счётном таргете).
- **Diagnostic: RMSE** (контроль крупных промахов на пиках).
- Срезы: по часам, дням недели, кластерам станций, отдельно на пиках.

*Слой 2 — классификация риска (`risk_empty/risk_full`, 15/60 мин):*
- **Primary: PR-AUC** (класс «отказ» редкий при пороге ≤1).
- **Operational: Precision / Recall / F1** при выбранном operational threshold (recall ↔ advance detection, 1−precision ↔ false-alarm).
- **Diagnostic: confusion matrix** (15 и 60 мин раздельно).

*Baseline (для MDD/ADR), по слоям:*
- Потоки: historical average by station/hour/day_of_week; yesterday/same-hour.
- Availability risk: persistence («состояние через 15/60 мин = текущему»).
- LightGBM обязан бить соответствующий baseline; сравнение фиксируется в ADR.

**Валидация:** только **time-series split**; дополнительно **rolling backtest** (train месяц N → test N+1) — даёт кривую обучения и материал для champion/challenger.

**Онлайн-метрики (в проде).**
- Считаются на **скользящем окне после появления delayed labels** (через 15/60 мин + накопление окна).
- **Online recall / false-alarm rate / F1** при фиксированном threshold — основные live-метрики.
- **PR-AUC — только офлайн/backtest** (в проде шумит, не SLO-метрика).
- **Дрейф (Evidently):** feature/prediction/target drift; HTML-отчёты в MinIO/MLflow.
- **Деградация → триггер:** если online F1 или recall при фиксированном threshold падает ниже SLO на скользящем окне → переобучение/алерт.
- Технические (latency, error rate, freshness) — в SLI/SLO (раздел рисков).

**Гейт промоута.** Кандидат промоутится в production только если на свежем hold-out/backtest **не хуже champion** по primary-метрике слоя (PR-AUC для риска офлайн; MAE для потоков) с минимальным порогом улучшения; иначе остаётся champion (rollback-защита).

## 9. Подбор модели (итеративно)

- **Итерация 0 — Baseline (по слоям):** потоки — historical average / yesterday-same-hour; риск — persistence. Нижняя граница, которую всё обязано бить.
- **Итерация 1 — Линейная/Poisson baseline model.** Простая модель на базовых фичах (время, лаги, погода) — sanity-check на нелинейность и сигнал.
- **Итерация 2 — LightGBM (основная).** Полный набор фичей: время в локальном NY, лаги/скользящие, погода, interaction `temp×hour`, фичи 5 ближайших станций, доля e-bike, метаданные станции. Для счётного таргета тестируются Poisson/Tweedie objectives; альтернатива — регрессия по `log1p(target)` с обратным `expm1`.
- **Итерация 3 — Тюнинг LightGBM** (`num_leaves`, `min_child_samples`, learning rate, регуляризация) через time-series CV.
- **Итерация 4 — XGBoost-челленджер.** Не обязателен для финального production, но нужен как challenger для проверки устойчивости выбора LightGBM. По открытым источникам разница маргинальна и зависит от тюнинга.

**Вне scope:** LSTM/CNN-LSTM и графовые сети — «возможное улучшение», в MVP не реализуем.

**Артефакты:** все итерации логируются в MLflow (параметры, метрики, модель) — воспроизводимое сравнение и история экспериментов.

## 10. Инференс

Система сочетает оба режима, потому что продуктовая логика требует online-прогноза, а обучение и мониторинг естественно выполняются batch-пайплайнами.

**Real-time (online) — основной для продукта.**
- FastAPI: `POST /predict/station` (одна станция), `POST /predict/batch` (список станций). Берёт текущее состояние из последнего GBFS-снепшота + фичи из feature store + champion-модель → возвращает `risk_empty/risk_full` на 15/60 мин.
- Champion-модель загружается из MLflow при старте сервиса (или при обновлении версии) и используется из памяти.
- `GET /health` для проверки живости. Допустимая задержка — единицы секунд.

**Batch (offline).**
- Airflow по расписанию: приём снепшотов, сборка фичей, переобучение, оценка, Evidently-отчёты, периодический пересчёт прогнозов по всем станциям (сохраняется в Postgres для дашбордов).
- Месячное переобучение на свежем CSV — тоже batch.

**Распределение по серверам.** Сбор raw-снепшотов остаётся на существующем сервере (данные переживают `terraform destroy`). Новый Terraform-managed сервер несёт MLOps-стек и обработку. Рекомендуемая логика: старый сервер собирает raw каждые ~5 мин, новый забирает/обрабатывает каждые ~15 мин.

## 11. Обратная связь

**Источники обратной связи для следующей итерации:**
1. **Delayed labels по availability** (из будущих снепшотов через 15/60 мин) — online recall/false-alarm/F1 на скользящем окне. Эти метки оценивают качество продуктового risk-layer, а не подменяют чистую разметку demand/returns из trip CSV.
2. **Месячный trip CSV** — чистый ground truth для потоков; запускает «настоящее» переобучение и переоценку.
3. **Дрейф (Evidently)** — feature/prediction/target drift как ранний сигнал.
4. **Технические сигналы и DQ-отчёты (Great Expectations)** — деградация свежести/доступности источников, рост доли отфильтрованных/stale-станций.

Эти сигналы замыкают цикл: деградация online-метрики или drift-alert → запуск retraining DAG → candidate-модель → quality gate на backtest/hold-out → promotion в MLflow или сохранение текущей champion-модели.

**MDD — Да.** Архитектурные решения принимаются на основе метрик: выбор модели через сравнение с baseline на backtest, промоут через quality gate, а ключевое решение по оптимизации системы оформляется через статистический тест и **ADR**. Пример применения MDD: выбор между расчётом признаков on-demand и чтением готовых признаков из online feature store — сравнение двух наборов latency, гипотезы H0/H1, p-value, итоговое решение в ADR.
